# 领域模型草案

状态：建议，等待首条业务链路设计确认。这里定义概念与不变量，不决定数据库表结构或 API 路由。

| 概念 | 含义 | 关键约束 |
| --- | --- | --- |
| Workspace | 记忆的归属与授权边界 | 可服务个人、团队或组织；授权模型待定 |
| Source / SourceVersion | 导入资料及其不可变版本 | 相同位置只在确定的来源版本内有意义 |
| ParseResult / Evidence | 标准化内容和定位信息 | 携带来源版本、解析器版本；可回到原文 |
| Memory | 当前可使用的记忆 | 归属空间，保留证据引用与当前版本 |
| ChangeSet / MemoryVersion | 提议、提交与撤销的变更 | 语义变更通过 writing；历史不可静默改写 |
| RetrievalContext | 为一次请求组织的记忆与证据 | 遵循权限、版本与输出预算 |
| Task | 导入、写入、整理等执行单元 | 状态与重试可追踪，不等同于一条记忆 |

## 首次实现前必须回答

1. 引用证据使用全局 ID，还是 `(source_id, revision, parse_id, evidence_id)` 组合？当前 Parse 草案只承诺 evidence ID 在一次解析结果内唯一。
2. 什么信息必须经过用户确认？置信度不等同于授权或事实真实性。
3. 冲突如何表示、解决和追溯？并发修正是否使用期望版本号？
4. 如何把失败重试与一次语义提交对应起来？幂等有效期与失败恢复边界是什么？
5. 删除、撤销、过期、权限收回分别如何影响检索和派生数据？

在这些问题确认前，不创建最终表结构或公共记忆 JSON Schema。
